// Where libjay answers differently from jconsole on purpose. The `? ` line
// says why. The snapshot records BOTH answers, so `jay-corpus record`
// re-measures the pair and fails if it has quietly converged — the signal
// that the note (and the entry in docs/coverage.md) should go.

// J has three character types — one byte per item, two, and four — and
// libjay has one. A literal is the byte-oriented type, which is what every
// corpus/j/literals.txt line holds libjay to; `u:` widens one, and the
// wider type differs from the narrow one only in how it is WRITTEN OUT,
// since the items and their codes are the same either way (`# u: 'é'` is 2
// and `3 u: u: 'é'` is `195 169` in both). libjay writes a character below
// 256 as that byte, so a widened literal shows the text it was written as
// rather than the two characters its bytes name, and a character `u:` made
// from a code between 128 and 255 shows as a byte no text can hold.
// Everything a wide character does apart from displaying agrees, and a code
// at 256 or above — every one that needs the wide type to exist — displays
// alike too.
u: 'é'
? a widened literal writes its bytes here and its characters there
u: 233
? a character between 128 and 255 writes as its byte here
10 u: 233
? a character between 128 and 255 writes as its byte here
3!:0 u: 'é'
? libjay has one character type, so widening does not change it

// The same one-character-type reading over the byte conversions: `2 u:`
// widens bytes into characters in J, which is where the two writings part,
// and a codepoint between 128 and 255 that `9 u:` answers with writes as
// its byte here and as its character there.
2 u: 8 u: u: 955
? widening bytes to characters changes only how they are written out
9 u: 200 200
? a character between 128 and 255 writes as its byte here

// Two whole numbers a double cannot tell apart. jconsole holds every
// number in a double once the verb is not one of the integer special
// cases, so `9007199254740992` and `9007199254740993` are the same value
// to its `*.`; libjay keeps them as the integers they were written as and
// answers their real least common multiple. The comparison tolerance is
// not what parts the two — the numbers are equal in the reference's
// arithmetic before any tolerance is consulted.
(9007199254740992) *. (9007199254740993)
? jconsole holds both in one double and libjay keeps them exact

// An empty of BOXES is acceptable numeric data on both sides — `#. 0$<1`
// is 0 there and here — but jconsole refuses the one dyadic decode whose
// left argument is not empty itself. It answers `(0$0) #. 0$<1` and
// `(0$<1) #. 0$<1` with the same 0, and `2 #: 0$<1` with the empty, so the
// refusal is not a rule about boxes; libjay reads an empty the one way
// everywhere.
2 #. 0$<1
? jconsole refuses this one dyadic decode and answers every other empty

// A refusal about an operand's TYPE where the frame is empty — nothing to
// apply the verb to — survives in the reference for some verbs and not for
// others. Which verbs those are is measurable and libjay follows it now
// (`^.`, `j.` and `r.` settle their domain from the whole argument), but
// DECODE reads the same way from the other end and does not: `(1;2;3) #. (i. 2 0 3)`
// and `(2 0 3 $ 0) #. 'hello'` are refused there while `(<1) #. (i. 0)` and
// `(i. 0) #. 'ab'` are 0 and the empty. libjay keeps one rule: a refusal
// about a fill's type never survives an empty frame, and one about the
// cells' SHAPES always does.
(1;2;3) #. (i. 2 0 3)
? the reference refuses this decode and answers (<1) #. (i. 0)
(2 0 3 $ 0) #. ('hello')
? the reference refuses this decode and answers (i. 0) #. 'ab'
(<'abc') #. (2 0 3 $ 0)
? the reference refuses this decode and answers (<1) #. (i. 0)
(<1) #. (i. 0)
? the reference answers this decode and refuses (1;2;3) #. (i. 2 0 3)
// A refusal about the cells' SHAPES survives an empty frame for a decode
// whose radices are real and not for one whose radices are a fill, and the
// two spellings say the same thing about the same verb:
// `(0 $ 0.5) #. (i. 2 0 3)` is a length error there and
// `(i. 0 0) #. (,5)` — 0 radices against 1 digit either way — is the empty.
// libjay keeps the cell-agreement refusals of the verbs that PAIR their
// cells and no others.
(0 $ 0.5) #. (i. 2 0 3)
? the reference keeps this length error and drops it for (i. 0 0) #. (,5)

// Two large arguments to `!` a double cannot tell apart. jconsole answers
// `1e10 ! (1e10 + 1e_4)` with 1.00234; the value is 1.0023631, which the
// digamma series gives independently, and the reference's difference of two
// log-gammas cancels catastrophically at that size. libjay's own quotient
// lands on 1.00238, no closer, and matching the reference here would mean
// matching its arithmetic rather than the mathematics. Where the difference
// of the two arguments is a small WHOLE number both sides are exact and
// agree, which is the ordinary case and is recorded in fuzz_found.txt.
(1e10) ! (1e10 + 1e_4)
? both sides lose this one; the reference's answer is not the value either

// `x C. y` over a left argument that is no permutation of y's items. The
// Dictionary defines the dyad for a permutation — a direct one or a boxed
// list of cycles — and says nothing about anything else. Thirty probes did
// not find a rule in what the reference does with one: `(_2 0 2) C. 'hello'`
// is `eolhl` there, `(_1 _2) C. i.4` is `0 1 3 2` and `(_2 _1) C. i.4` is
// `0 1 2 3`, which is neither the direct reading nor the flat cycle form
// `C. y` writes, and `(_1) C. i.4` and `(_3) C. (1;2;3)` disagree with both
// again. libjay refuses instead: an undefined argument is answered with a
// diagnostic that says which value makes it no permutation, rather than
// with a number fabricated to match behaviour nobody has specified.
(_2 0 2) C. 'hello'
? the reference's answer for a non-permutation is undefined; libjay refuses
(_3) C. (1;2;3)
? the reference's answer for a non-permutation is undefined; libjay refuses
(_1 _2) C. i.4
? the reference's answer for a non-permutation is undefined; libjay refuses
(_2 _1) C. i.4
? the reference's answer for a non-permutation is undefined; libjay refuses
(_1) C. i.4
? the reference's answer for a non-permutation is undefined; libjay refuses
C. (_2 0 2)
? the reference's answer for a non-permutation is undefined; libjay refuses

// `x ^. y` over a boxed y and a NEGATIVE x, which sends the logarithm into
// the complex domain. jconsole answers this one with NOTHING AT ALL — no
// value, no error, no output line — while `2 ^. (<1)`, the same sentence
// with a positive left argument, is a domain error. The Dictionary defines
// the logarithm on numbers, so a box is undefined either way; libjay
// refuses both alike rather than following the silence.
(_3) ^. (<1)
? jconsole answers this one with no output at all and refuses 2 ^. (<1)
(_3) ^. (<'abc')
? jconsole answers this one with no output at all and refuses 2 ^. (<1)
(_3) ^. (1;2)
? jconsole answers this one with no output at all and refuses 2 ^. (<1)

// `x I. y` over BOXES. The Dictionary defines the interval index for a
// sorted numeric list; libjay extends it to every element type that has an
// order, which is the same total order `/:` grades by — and for characters
// and symbols the reference agrees. For BOXES it does not: its comparison
// there tells apart only equal from unequal, so `(<2) I. (1;2;3)` is
// `1 0 1` — a 1 on both sides of the 0 — which no order can produce, and
// `(<5) I. (1;2;3)` is `1 1 1` although `/: ((<5);1;2;3)` puts the 5 last
// in both. libjay answers by the order it grades with.
(<'') I. (1;2;3)
? the reference's box comparison here tells apart only equal from unequal
(<'a') I. (1;2;3)
? the reference's box comparison here tells apart only equal from unequal
(<5) I. (1;2;3)
? the reference's box comparison here tells apart only equal from unequal
(<2) I. (1;2;3)
? the reference's box comparison here tells apart only equal from unequal

// A polynomial of the THIRD degree or higher with an infinite coefficient
// aborts jconsole's own root finder — `p. (_ 1 2 3)` and `p. (1 2 3 __)`
// are both stack errors there, which is an interpreter limit and not an
// answer the Dictionary describes. The same polynomials at the SECOND
// degree answer with roots that have no value, and libjay carries that
// reading up to any degree: an infinite leading coefficient over a
// non-zero constant term leaves no root, and the roots come back as
// `_.j_.`.
p. (_ 1 2 3)
? jconsole's root finder aborts on this one with a stack error
p. (1 2 3 __)
? jconsole's root finder aborts on this one with a stack error
p. (0 1 1 _)
? jconsole's root finder aborts on this one with a stack error
